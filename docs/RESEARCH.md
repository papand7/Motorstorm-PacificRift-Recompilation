## Race exposure loop (T113, 2026-10-27, runtime)

- `func_004C3778` reads 5 sample points (`std::vector<float2>` at `[this+0x1A4]`, 0x28 bytes): (0.15, 0.70), (0.325, 0.63), (0.50, 0.30), (0.675, 0.63), and a fifth. Emax `[this+0xC4]` = 50.0. VERIFIED (PT regs at the entry).
- The race exposure surface is `0x07EBA600` (16x16 FP16, pitch 128), as in the garage. Only CPU-read; the D3D12 backend must copy it back to guest memory (`rt_readback.h`), else the CPU reads 0 and `c33.x` = 1 + 0.7*(50-1) = 35.3. VERIFIED (arms A vs B).
- With write-back, G samples are 0.1-1.0 and `c33.x` settles near 1.04 on the beach shot. One zero sample still pins 35.3, and this happens in one race-intro shot (sample 0 = 0 from 182.8 to 219.6 s) while the presented colour at that point is not black. VERIFIED. Origin: see below.
- The luminance chain (VERIFIED, RSXI F/G): op 502 `fp_0074B181` writes `(tex2.rgb + 16*(1-tex2.a)*avg4(MRT1)^2) * (1 - tex0.z*tex0.w)` into `0x02195900` 320x180 FP16 from `0x07F2B600` (uniform 127,127,0 here), scene MRT1 `0x01650000` and the particle layer `0x0BA10000` (cleared to 0; the particle program writes colour 0). Single-tap copies take it down to 10x5 `0x022C1600`; op 545 `fp_0074C781` writes the 16x16 `0x07EBA600`. Every scene program writes MRT1 = colour/16 (`h[4] = h[0]*0.0625`). After the chain `0x01650000` is reused as a packed velocity buffer (ops 509-538), so a pixel no scene draw covers keeps 0 there.
- The shoreline strip (VERIFIED): the sea/sand strip under sample (0.15, 0.70) has no scene draw in MRT1 until the blended shore draws of `fp_07200641` (4848 bytes) render; with them it fills (MRT1 zero coverage 1.97 % -> 0.56 %, the rest being the 16-px right-edge band). The D3D12 backend read every FP with a fixed 4096-byte limit, so this program was truncated and its `TEX_bx2` helper undeclared (fxc X3004); no draws, MRT1 0, luminance 0, `c33.x` 35.3. Read through END (`rsx_fp_span.h`, `2562ba8`): `c33.x` 0.95-1.11 through the shot; with `RSX_FP_SPAN=0` on the same exe the white shot returns. Seven other race programs are 4160-4240 bytes.
- fxc folds `x != x` (Cg isnan) to false with or without `D3DCOMPILE_IEEE_STRICTNESS`, and the decompiler's `_o == _o` export guard with it (VERIFIED offline, `generated/analysis/t113/fxc/`). `fp_0074C781` relies on isnan; not the cause of this zero (inputs are UNORM), open as a latent difference.

## Bink frame selection and decode cost (2026-10-22, offline)

Static analysis of `generated/decrypted/EBOOT.elf` (helpers `generated/analysis/dis.py`, `callers.py`, `stubcalls.py`, `spu_grp.py`; listings `dis_5c4a40.txt`, `dis_bink.txt`). The Bink library is `0xC5D000`-`0xC74000` with its own TOC `0x10CE894`; the game reaches it through cross-TOC stubs `0x757E78`-`0x757F98`.

- **VERIFIED (code):** the movie player's per-frame update is `0x5C4A40`. Its loop at `0x5C65DC`-`0x5C668C` is: `BinkWait` (`0xC6C770`); if not waiting, `DoFrameAsyncWait(-1)` (`0xC70318`), `NextFrame` (`0xC6ED28`), `DoFrameAsync` (`0xC70540`), then `ShouldSkip` (`0xC6F088`); while it returns 1 the loop goes back to `DoFrameAsyncWait`, decoding the next frame in the same game iteration; otherwise it returns to render and flip. Skipped frames are decoded but never drawn or flipped.
- **VERIFIED (code):** clock. `RADTimerRead` (`0xC70798`) = ms since first call from `sys_time_get_system_time`. Lateness (in `ShouldSkip`, mirrored in `NextFrame`) = `(now - epoch[+0x2C0]) - (frames since epoch [+0x2B4 - +0x2C4]) * 1000 * FrameRateDiv / FrameRate`, scaled by a 16.16 speed factor. The audio position is not read; sound pause/resume (`0xC6CC40`) and `BinkPause` (`0xC6BBAC`) only reset or shift the epoch.
- **VERIFIED (code):** skip rule. Skip when lateness > `+0x2C8` = `2000 * FrameRateDiv / FrameRate` ms (two frame periods: 66 ms at 29.97 fps), at most **3 consecutive skips**: counter `+0x340` is compared `cmplwi 2`; at the 4th check it resets and the frame is shown. So a lagging player shows exactly one frame in four -- a fixed constant, not a measured ratio. `+0x33C` counts total skips; `+0x334` caches the answer per frame.
- **VERIFIED (code):** resync. Lateness > 725 ms sets `+0x338`; the next `NextFrame` pauses sound (`0xC6CC40(bink,0)`, which stops the cellAudio port), waits for the IO buffer, clears the epoch and resumes sound -- the probe's six Bink port-1 `PortStop`s. 1:1 presentation returns only when lateness falls below 66 ms: after a resync, or by decoding faster than 29.97 for long enough. Lateness accumulates; nothing else forgives it.
- **VERIFIED (code):** `DoFrameAsyncWait` polls SPU completion with `sys_timer_usleep(10)` (`0xC73694`). **Measured offline:** the runtime's usleep(10) sleeps ~530 us, so a completed frame is noticed 266 us late on average (p95 509 us; `generated/profile/bench/pollwake`). ~0.8% of a frame; guest scheduling does not trigger the skip mode by itself.
- **SUPPORTED (probe data):** at 31.6-31.8 decoded/s the display stayed at ~7.9/s for several windows: the accumulated lateness pays back at only (decode - 29.97) frames/s.
- **VERIFIED (probe `20261022-180551-lsfwd`):** at 30.01 decoded/s lateness never reached the 725 ms resync (max ~15 frames; 0 audio port stops against 6), but 4:1 still covered 17 of 52 windows. Each slow stretch puts the player over 66 ms, and the 0.04 frames/s surplus repays it slowly. In skip stretches the main thread sleeps 88 % in `DoFrameAsyncWait` (`lr 0xC704EC`), and the flip interval is 129 ms (median). 1:1 needs decode margin, not a clock change.
- **VERIFIED:** the port's vblank ticker runs at 62.5 Hz (16 ms `GetTickCount64` steps), not 59.94 Hz. Bink does not read it.
- **VERIFIED:** the intro is constant bitrate: every 256-frame block holds 20.8-20.9 MB of video, one keyframe in the file; block decode rate is uncorrelated with block size in all four runs (r -0.2..+0.05). Block 768-1024 is the slowest in three of four runs; its cause is NOT TESTED (content-dependent block types are the likeliest; not the thread sampler, whose window covered a normal block).
- **VERIFIED (whole-function bench, `generated/profile/bench/lsfwd`):** hot groups' roles. `0x10200` and `0xF530` are Bink's integer 8x8 IDCT (constants 2896/3784/-5352, dequant table at LS `0x197C0`); `0x120A8` -> `0x12108` decodes a block's coefficients bit by bit, dispatching each symbol through a jump table at `0x122D4` (`bi $r4`) to handlers in groups `122E8`/`12BB4`, which branch back with direct cross-group transfers (both are drain hops). One IDCT block cost ~1.4 us (~7 host cycles per SPU instruction); `mpyh`/`mpyu` were scalarised by clang (4x `imul` + extracts/inserts each).

## Bink decode throughput (2026-10-22)

- **VERIFIED:** the Bink taskset `0x0135D080` holds one task (task 0, image `456415131`); one decoded frame per event-flag wake (the diagnostic run counted 3160 wakes for the 3159-frame intro). Decode is serial on one SPU task, so its speed is the translated SPU code's single-thread speed.
- **VERIFIED:** fast profile, v0.15 fork + high-resolution usleep (`20261022-075236-usleep-hrtimer`): 10.49 frames/s (256-frame blocks 9.78-11.12); the busiest thread ran ~98% of the intro, the next ~60%, the render thread ~15%. The "5 FPS" figure was the diagnostic profile's logging cost.
- **VERIFIED:** on x86 the quadword byte rotates/shifts used a 16-byte scalar loop (upstream has NEON forms only); `rotqby` cost ~86 instructions and is the lifted Bink image's most-used permute (1509 sites). The generate-controls built their vector through a stack byte store and reload.
- **VERIFIED:** the guest `usleep(200)` site `0x004AF6D0` is a periodic service loop in `func_004AF670`: `func_004AC940(obj)`, `func_004AE908(obj)`, sleep, until byte `obj+0x4064` is set. It does not wait on one condition the host could signal.
- **STRONGLY SUPPORTED:** D3D12 is not the limit for the intro (render thread ~15% of a core).
- **HYPOTHESIS:** the remaining per-instruction cost is dominated by the register file living in `ctx->gpr[]` (a load and store per SPU op) and by per-step drain hooks; a lifter-level register cache is the next large lever.
