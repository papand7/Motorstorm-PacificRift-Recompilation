# T122: D3D12 GPU submission and synchronisation

Worktree `ps3recomp-t122`, branch `agent/t122-d3d12-submission`, local only (nothing merged or pushed). Base: T113 `2562ba8`.

Host: Ryzen 5 9600X, RTX 5060 (display, 144 Hz), and the 9600X's 2-CU RDNA2 iGPU ("AMD Radeon(TM) Graphics", `CELLMARK_IGPU=1`). **No Radeon 890M was available. Nothing here is an 890M result.**

## 0. Summary

- **GPU synchronisation is not a race bottleneck (VERIFIED, 23 race runs, both GPUs).**
  - Waits are 0.00 ms per frame, with 0 blocked waits, measured on the current code.
  - GPU time per frame: 3–7 ms on the RTX, 11–18 ms on the iGPU. A frame takes ~200 ms.
  - Overlap (pipelining) has nothing to recover, so it was **not implemented**. The sync investigation is closed.
- **The largest renderer CPU cost was the texture snapshot (VERIFIED).**
  - It took 63 of the 74 ms the draw callbacks spend per race frame.
  - Cause: one 2 MB linear B8 texture, never rewritten, re-hashed on ~1340 draws per frame, about 2.7 GB per frame.
  - T119's offline bench could not see this, which explains its "in-game 107 ms vs offline 40 ms" gap.
- **Fixed, opt-in (`54a25df`, `PS3_TEX_SNAPSHOT_EPOCH=1`):** a texture is hashed once per RSX sync epoch.
  - RSX drain: 77 → 15.6 ms per frame with T119, 115 → 53 ms without it.
  - Images and Bink video: no regression (§7).
- **FPS did not change (4.9–5.1 in every arm), and this is a concrete limitation (VERIFIED).**
  - In this base the race is guest-bound: the RSX thread is idle 80–170 ms of each ~200 ms frame.
  - Removing 60 ms (epoch) or 100 ms (epoch + T119) of RSX work only increases that idle time.
  - The frame rate is set by the guest PPU/SPU side. T106 measured guest maxContention at +57% (`b84ed80`, T109 line), and it is not in this base.
- **Next step:** integrate guest maxContention (T106/T123 owners) with T119 and the epoch, then re-measure.
  - In T106 maxContention made the RSX thread the bound (busy ~130 of 134 ms).
  - The ~100 ms of RSX work removed here then becomes frame time.

## 2. Submission architecture (VERIFIED, code reading)

- Everything runs on one frame-clock thread: FIFO drain, draw callbacks (expand plus snapshot) and `render_frame`.
- Per pass, `render_frame` does:
  - the entry `wait_for_gpu` (full drain);
  - allocator and list reset;
  - atlas upload (dirty);
  - RT pre-pass;
  - per record: SRV window, texture uploads, PSO, transitions and draw;
  - one `ExecuteCommandLists`;
  - `Present(1,0)` on the presenting pass;
  - `move_to_next_frame`.
- Passes per guest frame = 1 + early replays: 2 in the base race, 1 with T119 compact.
- Guest-required orderings: draw order (one queue), RT write-back before the guest reads it (T113 `rtrb`, its own fence and thread), and flip order.

## 5. Decisions

- **Overlap / pipelining: rejected on measurement (VERIFIED).**
  - The §8 rule from the earlier report needed an entry wait ≥ 3 ms per frame and GPU time ≥ 0.8× the frame. Measured: wait 0.00 ms; GPU time 2–9% of the frame on the RTX and 5–9% on the 2-CU iGPU.
  - The GPU finishes long before the next pass is recorded, so overlap would hide nothing.
  - An 890M has ~8× this iGPU's CUs, so GPU time would be smaller still (HYPOTHESIS).
- **Largest remaining CPU cost on the RSX thread: the texture snapshot.** It was fixed here (§6).
  - It does not overlap T119 (vertex path), T115B (upload validation in `vp_upload_tex_slot`) or T116 (PSO).
  - After the fix, the T119 build's RSX work per frame is: drain 15.6 + record 8.5 + rest ≈ 28 ms of a 196 ms frame.
- **What limits FPS now: the guest side (VERIFIED, as a limitation).**
  - The RSX thread idles 168 ms per frame in NE.
  - In T106, `PS3_SPURS_GUEST_MAXCONT` (+57%) moved the bound to the RSX thread. That commit (`b84ed80`) is on the T109/T123 line and does not apply to `2562ba8` (`git apply` fails in `cellSpurs.c`). SPURS changes are outside T122's scope.
  - **Prediction (HYPOTHESIS):** with maxContention, T106's RSX-bound frame of ~134 ms would drop by the ~100 ms removed here (T119 plus epoch), until the guest side binds again. T106's guest-side numbers suggest that is around ~95 ms per frame.

## 6. `PS3_TEX_SNAPSHOT_EPOCH` (`54a25df`)

- **Why the hashing exists:** the snapshot (PS3_TEX_SNAPSHOT, default on) captures eligible textures at draw-record time, so a guest that reuses a buffer after a sync signal (Bink) cannot tear the upload. It hashed every eligible texture on every draw.
- **Epoch:** `g_cellGcm_sync_epoch` in `cellGcmSys.c`, one relaxed atomic add. It is bumped:
  - at every drain pass;
  - at a JUMP's published `get`;
  - before every packet that is not a 3D state/draw method on subchannel 0. That covers methods below 0x0180 (NV406E semaphores, SET_REFERENCE, NOTIFY, WAIT_FOR_IDLE), CLEAR_REPORT_VALUE, GET_REPORT, 0x1D6C–0x1D74, and every other subchannel (flips, user commands, transfers);
  - after every render-target write-back (`rtrb`, on its own thread).
- **With the switch on:** a key already captured in the current epoch is reused without a hash. Between two bumps the guest gets no information about RSX progress and no RSX-side guest write happens, so the two draws reading the texture "at the same instant" is a valid hardware outcome. A guest write between them would also race on hardware.
- **Off by default.** Unset, the code takes exactly the old path (`epoch_src` NULL). The walker's bump is always maintained, at one atomic add per pass, JUMP or impure packet.
- **Regression found and fixed in this work:** `17363cc` made passes without a Present wait in `move_to_next_frame` for their own list. The first race run showed it: 1 blocked wait and 2.6 ms per frame. `a0670df` restores the base condition, and the re-runs show 0 blocked waits.

## 8. Integration

- The epoch touches `cellGcmSys.c` (walker), `tex_snapshot.h` and the backend. No other branch edits these hunks; T115B's `vp_record_tex_snap` change merges cleanly.
- **Recommended:** turn `PS3_TEX_SNAPSHOT_EPOCH` on by default after a reviewer checks the pure-packet list in `gcm_epoch_pure()`. It is the only judgement call: a 3D method that writes guest memory and is missing from the list would need adding.
- Then integrate T119 compact and guest maxContention, and repeat this A/B (commands in §9). Expected RSX busy time is about 28 ms per frame on this PC.

## 10. Limitations

- No 890M. The iGPU here is a 2-CU part.
- This base lacks guest maxContention, so the FPS effect of the RSX savings is unmeasured until that is integrated.
- One NA run and one IE run. The NC/IC repeats spread ±7%.
- The scene is the race-start flyby, not driving.
- The race image check is not pixel-exact (timing differences).
